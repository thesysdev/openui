A live dashboard is built once by a model and loads fresh data every time someone opens it, with no model call. Claude Data does this inside Claude, and we [took it apart](/blog/how-claude-dashboards-work) earlier this month. Plenty of teams want the same thing inside their own app.

We built one and open-sourced it. [OpenDashboards](https://github.com/thesysdev/opendashboards) lets you connect a database or an analytics tool, ask for a dashboard in plain English, and keep refining it by chat.

It's built on [OpenUI Lang](/docs/openui-lang/overview). The model writes a short program that names components from your library, and a `Query` in that program names one of your data tools, so the renderer loads fresh data every time the dashboard opens. OpenUI Lang has worked this way since v0.5 in April.

Under the hood, OpenDashboards uses the [OpenUI Dashboards API](/docs/dashboards) to build and serve each dashboard. Here's what that API does, if you want to build something like it into your own app.

## Getting the numbers right

A model can write a dashboard that looks fine and shows the wrong thing: a chart that reads a column that doesn't exist, or a total over the wrong rows. This is where we put most of our effort.

- **A prompt tuned for dashboards.** It's generated from your component library, with rules for what makes a good dashboard: how to lay out a page, when to add filters and previous periods, how to label numbers.
- **Checks before and after the model writes.** Before, the model looks at your data by calling your tools, so its charts are bound to fields that exist. After, we check that every query and script it wrote matches the shape of what your tools actually return: a chart reading `rows.revenue` when the rows have `amount` is caught before anyone sees it.
- **A replay before saving.** The finished dashboard and its scripts are run again on the server with your real data. Anything that would come out empty or broken goes back to the model to fix, so broken charts are caught before anyone opens the dashboard, without a round of "this chart is empty, fix it".

We built it to work with any size of model, so you can choose by cost. On our hardest set of requests (funnels, retention cohorts, web vitals, revenue against a target), Claude Haiku 5.5 scored 110 out of 120 in a blind review with these checks, against 94 on its own. On its own, about 1 in 7 of its dashboards broke; with the checks, none did. DeepSeek v4.1 Flash built every test dashboard correctly at a third of a cent per build.

## Keeping it safe

OpenUI Lang has no HTML or JavaScript in it. The model names components from your library, and data comes in through `Query`, which calls one of your tools and puts its result straight into those components. There's no code between your data and the screen, so a dashboard on its own can't run code.

Some numbers need real logic, like grouping customers by age or combining two tools into one metric. For those, the model writes a small JavaScript script. Scripts make dashboards far more flexible, but they're code a model wrote. If they ran in the browser, anyone could build a dashboard with a harmful script, share it, and have it run in every viewer's browser with that viewer's access.

So scripts have to run on the server, in a sandbox that:

- **starts fresh and empty every time:** no network, no filesystem, thrown away after each run, with hard limits on time and memory so a runaway script stops;
- **can call your other tools safely:** only the tools you registered, each call running on your server with the viewer's own access, so a script can combine data without reaching anything it shouldn't;
- **keeps code on the server:** browsers get the dashboard, never the script, and nobody can swap in code of their own.

The browser needs care too. It has to load a user's dashboards without ever holding your API key, which takes a short-lived token, minted by your server for one user, signed so it can't be altered to claim someone else, and refreshed before it expires.

## Edits and live updates

People don't build a dashboard once. They refine it, share it, and leave it open on a second screen.

**Edits that keep what's there.** "Add a pie chart by payment method" should add a pie chart, not rebuild the dashboard and lose the filters someone tuned. OpenUI Lang's [incremental editing](/docs/openui-lang/incremental-editing) makes that possible: the model writes only the parts that change, and they're merged into the dashboard. Around it you need the same checks as a new build, everyone kept on the current version until the new one is ready, and a guard so two people editing at once can't overwrite each other.

**Live updates for everyone watching.** A dashboard being built should appear at once for everyone looking at it and fill in as it's written, showing only the dashboard, never the model's commentary or script code. Open dashboards should pick up a new version, a rename or a change in access on their own, reconnect when the connection drops, and show a build that has stopped making progress as stalled instead of spinning forever.

## Storage and sharing

A dashboard in your product belongs to one of your users, and nobody should see data that isn't theirs. That takes two things:

- **Storage that knows who owns what.** Each dashboard is saved with its owner, its program and its scripts, and the scripts stay on the server. A dashboard is saved as soon as its build starts, so it can be listed, shared or deleted before it's finished. The data the model looked at while building stays with the user who built it. For fast opens, each viewer's last results are kept for up to a day and are only shown for the version they came from. Your data tools themselves always run on your own server; while a dashboard is being built, the results the model looks at pass through to the model provider you chose.
- **Sharing without sharing data.** When someone shares a dashboard with a person or a team, they share its layout and queries, never its results. Queries run as whoever is viewing, so your data tools can give two people different numbers on the same dashboard. Access is checked on every request, so removing a share takes effect on the next one, and someone without access can't tell the dashboard exists. Team membership travels in the token, so removing someone from a team takes effect when their token expires, within 15 minutes.

## Use the OpenUI Dashboards API

The OpenUI Dashboards API gives you a build harness tuned for dashboards that does all of the above out of the box, including a sandbox that runs each script in a fresh QuickJS virtual machine compiled to WebAssembly. Integrating it takes one definition:

```ts title="lib/openui.ts"
import { OpenUIClient } from "@openuidev/server";
import spec from "../generated/spec.json"; // generated from your component library by the OpenUI CLI
import { dataTools } from "./data"; // functions on your server that return data

export const dashboards = new OpenUIClient().defineDashboard({
  library: spec,
  model: "anthropic/claude-sonnet-5.5",
  tools: dataTools,
});
```

Give `dashboards.create()` and `dashboards.edit()` to your chat agent as tools, or call them from your own code. The renderer shows the result in your app, drawn with your components.

- **Start building** with the [OpenUI Dashboards docs](/docs/dashboards), or create the example app in one command: `npx @openuidev/cli@latest create --example assistant-ui-dashboards`.
- **See a complete app** in [OpenDashboards](https://github.com/thesysdev/opendashboards), or use it at [opendashboards.com](https://opendashboards.com).

The Dashboards API is part of OpenUI Cloud, which has a [free tier](/docs/gateway/pricing-credits).
