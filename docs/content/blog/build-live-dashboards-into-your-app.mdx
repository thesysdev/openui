A live dashboard is built once by a model and loads fresh data every time someone opens it, with no model call. Claude Data does this inside Claude, and we [took it apart](/blog/how-claude-dashboards-work) earlier this month. Plenty of teams want the same thing inside their own app.

We built one and open-sourced it. [OpenDashboards](https://github.com/thesysdev/opendashboards) lets you connect a database or an analytics tool, ask for a dashboard in plain English, and keep refining it by chat.

It's built on [OpenUI Lang](/docs/openui-lang/overview). The model writes a short program that names components from your library, and a `Query` in that program names one of your data tools, so the renderer loads fresh data every time the dashboard opens. OpenUI Lang has worked this way since v0.5 in April.

Under the hood, OpenDashboards uses the [OpenUI Dashboards API](/docs/dashboards) to build and serve each dashboard. Here's what that API does, if you want to build something like it into your own app.

## Getting the numbers right

A model can write a dashboard that looks fine and shows the wrong thing: a chart that reads a column that doesn't exist, or a total over the wrong rows. This is where we put most of our effort.

- **A prompt tuned for dashboards.** It's generated from your component library, with rules for what makes a good dashboard: how to lay out a page, when to add filters and previous periods, how to label numbers.
- **Checks before and after the model writes.** Before, the model looks at your data by calling your tools, so its charts are bound to fields that exist. After, tools verify that every query and script it wrote matches the shape of what your tools actually return.
- **A replay before saving.** The finished dashboard and its scripts are run again on the server with your real data. Anything that would come out empty or broken goes back to the model to fix, so the dashboard works the first time someone opens it, without a round of "this chart is empty, fix it".

We built it to work with any size of model, so you can choose by cost. On our hardest set of requests (funnels, retention cohorts, web vitals, revenue against a target), Claude Haiku 5.5 scored 110 out of 120 in a blind review through the harness, against 94 on its own, and none of its dashboards broke. DeepSeek v4.1 Flash built every test dashboard correctly at a third of a cent per build.

## 2. Running model-written scripts safely

OpenUI Lang has no HTML or JavaScript in it. The model only names components from your library and the tools that feed them, and the renderer draws nothing else, so a dashboard on its own can't run code.

Some numbers need logic, though, like grouping customers by age from their birth dates or combining two tools into one metric. For that, the model writes a small JavaScript script. Scripts are what make dashboards flexible, and they're also code a model wrote. Run them in the browser and anyone could build a dashboard with a malicious script, share it, and have it run in every viewer's browser with that viewer's access. So scripts never run in the browser.

**A fresh sandbox for every run.** Each script runs on the server in a new QuickJS virtual machine, compiled to WebAssembly, in its own worker, and is thrown away afterwards. The script gets your tools, its arguments and a console, and nothing else: there's no network to call and no filesystem to read.

| Limit | Value |
| --- | --- |
| CPU | 500 ms of compute at a time |
| Time | 2 s between tool calls, then the run is stopped |
| Memory | 64 MB |
| Tool calls | 48 per run |

**Your tools, run as the viewer.** A script never reaches your tools directly. It pauses, its calls go back to your server to run with the viewer's own access, and it resumes with the results. The paused state travels as a signed token, so it can't be altered, and it's useless after 10 minutes.

**Scripts stay on the server.** Browsers only ever receive the dashboard's program. The API looks up a script's code itself from the saved dashboard, and a request can't supply code of its own. As a second layer, every script is checked before it's saved: it must parse and call only your tools, and one that reaches for `fetch`, `eval` or `require` is rejected.

## 3. Auth and sharing

A dashboard in your product belongs to one of your users, and everyone else must only ever see their own data.

**Per-user tokens in the browser.** The browser has to read a user's dashboards without holding your API key. Your server mints a short-lived token with its key: it's scoped to one user, lasts 15 minutes, and can carry the user's groups. The organization always comes from your key, never from the browser, and a token can't be changed to claim another user. The client refreshes it before it expires.

**Sharing that never shares data.** A dashboard is private to whoever created it. Its owner can share it with a user or a group, to view or to edit, and access is checked on every request, so removing a share takes effect at once. A shared dashboard shares its layout and queries, never results: its data tools always run as the viewer, and its scripts only run for users who can see it. Someone without access gets the same "not found" as for a dashboard that doesn't exist. Even while a dashboard is being built, each user's tool results are kept apart, so someone editing a shared dashboard never sees another user's data. Groups are yours, and OpenUI never stores who's in them.

## 4. Edits and live updates

People don't build a dashboard once. They refine it, share it, and leave it open on a second screen.

**Edits that keep what's there.** "Add a pie chart by payment method" should add a pie chart, not rebuild the dashboard and lose the filters someone tuned. OpenUI Lang's [incremental editing](/docs/openui-lang/incremental-editing) makes that possible: the model writes only the statements that change, and they're merged into the program. The API checks the merged program, keeps scripts that didn't change exactly as they were, and keeps everyone on the current version until the new one is ready; a failed edit leaves the dashboard as it was. A write only applies to the version it started from, so a second edit while one is running is told to try again instead of overwriting it.

**Everyone watches the build.** A dashboard being built appears at once for everyone looking at it, showing what the builder is doing, then fills in as it's written. Viewers receive only the dashboard, never the model's commentary or any script code. If a connection drops, the page reconnects on its own, and an open dashboard picks up a new version, a rename or a change in access within 30 seconds. A build that stops making progress is marked as stalled instead of spinning forever.

**Fast opens.** The API keeps each viewer's last results for up to a day and shows them the moment a dashboard opens, while the live queries catch up.

## 5. Models and cost

A build makes several model calls with the same long prompt, and the model and effort you pick decide how fast and how expensive it is. We saw both effects in our own runs.

**Effort is the biggest lever.** At default effort, Claude Sonnet 5.5 spent most of its output on hidden thinking, and a dashboard edit took five minutes. The API takes one reasoning-effort setting and translates it into each provider's own form, so you can set it once and switch models freely. That's how OpenDashboards went from 301 seconds to 90 for the same edit.

**Caching does the cost work.** The dashboard prompt is long and repeats across the rounds of a build, so the API caches it. Sonnet's first signups build cost about 5 cents; the next ones cost about 1 cent, because the prompt was already cached.

**The model sets your price.** With the prompt cached, a build cost 1 to 3 cents in model usage on Claude Sonnet 5.5 and Gemini 3.8 Flash, and a third of a cent or less on DeepSeek v4.1 Flash, at list prices. You pick the model with one string, across hundreds of models from Anthropic, OpenAI, Google and others. When a provider fails, the request moves to the next one, and you can bring your own provider key.

## Use the OpenUI Dashboards API

The OpenUI Dashboards API does all of the above. On your side, it's one definition:

```ts title="lib/openui.ts"
import { OpenUIClient } from "@openuidev/server";
import spec from "../generated/spec.json"; // generated from your component library by the OpenUI CLI
import { dataTools } from "./data"; // functions on your server that return data

export const dashboards = new OpenUIClient().defineDashboard({
  library: spec,
  model: "anthropic/claude-sonnet-5.5",
  tools: dataTools,
});
```

Give `dashboards.create()` and `dashboards.edit()` to your chat agent as tools, or call them from your own code. The renderer shows the result in your app, drawn with your components.

## Methodology

Quality: Claude Haiku 5.5 built six dashboards from the same chats (web analytics, a funnel, retention, web vitals, revenue, and traffic against orders), once as a single call and once through the harness. Each finished dashboard was captured in full and scored blind out of 20, on whether it answered the request, whether its data looked right, its clarity, and whether its filters fit. Correctness: 27 dashboard requests over public data APIs, each build's queries run again afterwards. Edit time: the same web-analytics edit, five runs per setup, median. Costs: model usage at OpenRouter list prices. The limits in this post were read from the OpenUI Dashboards API's code on November 27, 2026, and can change.
