## What are OpenUI Dashboards?

OpenUI Dashboards lets the agent in your own app build live dashboards. A user asks for one in chat, such as "orders and refunds by day for the last 30 days, with a status filter", and gets a dashboard drawn with your components. The agent builds it once. After that, every time it opens, it loads fresh numbers through your own data tools, with no model call. Every number on it can show where it came from.

If that sounds like Claude Data (launched as Claude Dashboards), it should. In [How Claude Dashboards work](/blog/how-claude-dashboards-work) we took Anthropic's design apart and found that it keeps the model out of the page at view time, the same idea OpenUI Lang is built on. This post is the other half: the same design, as something you put in your own product.

We also built a complete app on it and open-sourced it. [OpenDashboards](https://github.com/thesysdev/opendashboards) connects to your databases and analytics and builds dashboards from a chat. It's MIT-licensed: run it, fork it, or read how every part works.

## The same design underneath

Our earlier post started from what a dashboard has to do that a chat answer doesn't. A chat answer is written once, for one person. A dashboard is opened again next week, by people who weren't in the chat, and its numbers have to be current, traceable and cheap to look at every time.

Claude Data and OpenUI Dashboards solve that the same way. The model writes down where each number comes from and how to draw it, once. A fixed runtime then loads the data and draws the dashboard for each reader, with no model call. Where they differ is who owns each piece:

| | Claude Data | OpenUI Dashboards |
| --- | --- | --- |
| **Model** | Claude | Hundreds of models, including Claude, Gemini and DeepSeek |
| **Where it runs** | Inside Claude | Your product |
| **What the model writes** | Stored documents: datasets, calcs, and an HTML page with JavaScript | One program in [OpenUI Lang](/docs/openui-lang/overview) |
| **What draws it** | HTML and d3 the model writes (design systems since GA) | Your component library |
| **Where data comes from** | The reader's connectors, called by claude.ai | Your data tools on your server, or an MCP server |
| **Where a number comes from** | Sources panel, for numbers the model marked | Sources panel, traced from the program for every component |
| **Cost** | Each builder's paid Claude plan | Per build, set by the model you pick: 1–3 cents, or under a cent |
| **Sharing** | Inside Claude | With users and groups in your app, each reader on their own data |
| **Code** | Closed | Renderer, component library, SDK and OpenDashboards are MIT |

## Speed

In Claude Data, the model writes a small tree of documents: one dataset per source, calcs that derive values, and an HTML page whose scripts fill in placeholders. The signups dashboard from our earlier post was 12 to 14 KB of page code for two numbers and a bar chart.

In OpenUI Dashboards, the model writes one short program that names your components and the data behind them:

```text
$weeks = "8"
root = Stack([filter, chart])
filter = Select("weeks", [SelectItem("4", "Last 4 weeks"), SelectItem("8", "Last 8 weeks")], null, null, $weeks)
weekly = Query("weekly_signups", {weeks: $weeks}, {rows: []})
latest = @Last(@Sort(weekly.rows, "week_start"))
chart = BarChart(weekly.rows.week_start, [Series("Signups", weekly.rows.signups)])
```

Each line maps to a part of Claude's design. `Query` is a dataset: a tool, its arguments and a default shape. `latest` is a calc, written with built-in `@` functions instead of JavaScript. `$weeks` is a param, and the query runs again when it changes. `BarChart` is a draw, except the model doesn't write it: it's a component in your library.

Less to write means less to wait for. We gave both the signups example from the earlier post: eight weeks of numbers, and the ask "show last week's number, the change on the week before, and a bar chart per week".

| | Time to a finished dashboard (median of 3) | Right numbers |
| --- | --- | --- |
| Claude Data on claude.ai (default model, Opus 5.5) | 1 min 53 s | 3 of 3 |
| OpenUI Dashboards, Claude Sonnet 5.5 | **7.6 s** | 3 of 3 |
| OpenUI Dashboards, DeepSeek v4.1 Flash | 16.5 s | 3 of 3 |
| OpenUI Dashboards, Gemini 3.8 Flash | 26.9 s | 3 of 3 |

That's about 15 times faster on Sonnet. It compares products, not models: a chat product timed with a stopwatch, against an API call. Most of the gap is likely the output itself, a page of HTML and JavaScript against six statements. See the [methodology](#methodology).

Speed doesn't cost correctness. Before a dashboard is saved, it's rendered on the server with the real results of its queries, and anything that would render wrong, such as a chart reading a field the data doesn't have, is repaired. Claude Data checks its page too, but only once it's open in someone's browser.

## Open source

Everything you need to put dashboards in your product is MIT-licensed and on GitHub:

- **The renderer** (`@openuidev/react-ui`), which draws a dashboard and runs its queries.
- **The component library** (`@openuidev/dashboard-library`): KPIs, time series, bars, funnels, tables, maps and filters.
- **The SDK** (`@openuidev/server`), which defines how dashboards are built and runs your data tools.
- **[OpenDashboards](https://github.com/thesysdev/opendashboards)**, a complete app built on all three.

The step where the model writes and checks the dashboard runs on the OpenUI Cloud API.

OpenDashboards is what OpenUI Dashboards looks like as a whole product. You connect your data, chat with an agent that explores it first, and get dashboards you keep refining in the same chat. It connects to Postgres, Supabase, Neon, MySQL, ClickHouse, BigQuery, PostHog, Google Analytics, Search Console and remote MCP servers, and it has workspaces, sharing and a Sources panel on every dashboard. Use the hosted version at [opendashboards.com](https://opendashboards.com), or run it yourself:

```bash
git clone https://github.com/thesysdev/opendashboards.git
cd opendashboards
pnpm install
cp .env.example .env.local   # then add THESYS_API_KEY
pnpm db:up
pnpm db:reset
pnpm dev                     # http://localhost:3000
```

You need Node 20.9 or later, pnpm, Docker, and a Thesys API key from [console.thesys.dev](https://console.thesys.dev); OpenUI Cloud has a free tier. Fork it as the start of dashboards in your own product, or read it as a reference integration.

## Data provenance

A number on a dashboard is only useful if a reader can trust it without asking the model. This is the part we put the most work into.

Claude Data's answer is the Sources panel. Click a number and it shows the dataset or calc behind it: the stored query, the formula and the rows. But it only works for numbers the model marked. In Claude's design, each number on the page is a placeholder that names its source in `data-source` and `data-field` attributes. If the model leaves a mark out, that number can't be traced, and draws never appear in Sources at all.

OpenUI Dashboards traces sources from the program itself. Every component and every prop can be followed back through the statements in between to the queries that fed it, because that's how the program is written: `chart` reads `weekly.rows.signups`, and `weekly` is a `Query`. The model doesn't mark anything, so it can't forget to, and the bar chart is as traceable as the headline number.

It's one prop on the renderer:

```tsx
import { LiveArtifactRenderer } from "@openuidev/react-ui/cloud";

<LiveArtifactRenderer id={id} library={library} interpreter={interpreter} enableProvenance />;
```

The renderer's bar gets an inspect toggle. With it on, clicking a component, or a number inside one, selects it instead of acting, and a Sources panel docks beside the dashboard. It shows:

- **Queries:** the tool that was called, the exact arguments of the call behind what's on screen, and its result.
- **Formula:** each statement between the query and the value, such as `latest = @Last(@Sort(weekly.rows, "week_start"))`.
- **Filters:** the `$variables` the value reads, with their current values.

The panel is yours to replace: build your own Sources panel in your design, name your tools in your users' words, or add a "copy query" button. It works with any component library, with no change to your components.

## Cost

The model is called to build or edit a dashboard, and that's all. Opening it, filtering it and refreshing it load new data into the same layout through your tools, with no model call. Edits are cheap too: "add a pie chart of revenue by payment method" patches only the statements it describes, and the rest of the dashboard, its filters and its queries stay as they are.

We built the signups dashboard and a 14-day website-traffic dashboard on PostHog with three models, three times each:

| Model | Signups | Website traffic | Cost per build, at list prices |
| --- | --- | --- | --- |
| Claude Sonnet 5.5 | 7.6 s | 14.0 s | 1–3 cents |
| Gemini 3.8 Flash | 26.9 s | 14.3 s | 1–3 cents |
| DeepSeek v4.1 Flash | 16.5 s | 38.1 s | a third of a cent or less |

All 18 builds were saved and every panel had data. DeepSeek was 4 to 40 times cheaper than the others and just as correct here, though slower and less predictable from build to build. A first build costs more, before the prompt is cached: about 5 cents on Sonnet.

Claude Data runs on Claude, and building counts against each user's paid Claude plan. With OpenUI Dashboards, your users don't need an AI plan: they use your product, and you pay per build.

## Any model

Claude Data is built by Claude. OpenUI Dashboards can be built and edited by hundreds of models from providers such as Anthropic, OpenAI and Google, set with one line:

```ts
model: "anthropic/claude-sonnet-5.5", // or "google/gemini-3.8-flash", "deepseek/deepseek-v4.1-flash", …
```

That lets you choose per product, or per kind of user: a fast model for small dashboards, a cheap one for high volume, the strongest one for your most complex data. The model's output is always checked against your component library and your real data before it's saved, whichever model wrote it. See the [model list](/docs/gateway/models).

## In your product

Claude Data lives inside Claude. OpenUI Dashboards lives inside your app, in three ways.

**Your components.** A dashboard renders only with the component library you pass in. The prebuilt dashboard library works without setup, and moving to your design system later changes the library, not the integration. The model can only use components that exist, so every dashboard looks like the rest of your app. Claude Data now supports design systems too, but its dashboards still live in Claude.

**Your data.** A dashboard loads its data through data tools: functions on your server that return JSON, or tools from an MCP server. The model sees each tool's description, arguments and an example output while it builds. The browser runs the tools through an interpreter route on your server every time the dashboard opens, and a query can also refresh on an interval while it's open. When a value has to be combined from several tools, the model writes a small script that runs in OpenUI's JS interpreter with secure execution and can call only your tools.

```ts title="lib/openui.ts"
import { OpenUIClient } from "@openuidev/server";
import spec from "../generated/spec.json";
import { dataTools } from "./data";

export const dashboards = new OpenUIClient().defineDashboard({
  library: spec,
  model: "anthropic/claude-sonnet-5.5",
  tools: dataTools,
});
```

**Your agent.** The agent you already have calls `dashboards.create()` or `dashboards.edit()` as a tool, and the chat renders the result: as a card in the conversation, in a side panel, or on its own page. The [OpenUI Dashboards docs](/docs/dashboards) show the full integration.

Credentials stay on your side. Your API key authenticates your server and never reaches the browser, which gets a short-lived token scoped to one user. The model can call only the tools you register, and the page runs no model-written code: the renderer draws your components and calls your tools, and anything else is an error. Your routes still need to check who the user is and validate the arguments, as for any other API.

## Sharing

A dashboard is private to the user who created it. Its owner can share it with a user or a group, to view or to edit:

```tsx
import { useArtifactShare } from "@openuidev/react-ui/cloud";

const { share } = useArtifactShare();
share(dashboardId, { type: "group", id: "team:finance", access: "view" });
share(dashboardId, { type: "user", id: "user_42", access: "edit" });
```

A shared dashboard shares its layout and queries, never the sharer's data. Its data tools always run with the viewer's own context, so each reader sees exactly what their own access allows. Groups are yours: OpenUI never stores who's in them. Editors can change the dashboard with a prompt; viewers can open, filter and refresh it.

Claude Data's dashboards are shared inside Claude, and its page is code the model wrote, so Anthropic sandboxes it and keeps connector credentials on its own servers. When we tested the beta, page code could ask for any tool on the reader's connectors, each behind a consent card, and a test write went through after one consent click. Anthropic now says viewers of a shared dashboard see only the queries an editor approved. We haven't retested since the general release.

## Try it

- **Use it:** [opendashboards.com](https://opendashboards.com), or [clone OpenDashboards](https://github.com/thesysdev/opendashboards).


## Methodology

Claude Data: claude.ai, November 26, 2026, the account's default model (Claude Opus 5.5), the signups prompt with the numbers pasted in, three new chats, timed until the dashboard was drawn. OpenUI Dashboards: the production API through `@openuidev/server` 0.5.2, November 25, 2026, three runs per model, timed until the dashboard was saved; every saved query was run again to check its data. Costs are at OpenRouter list prices. The two sides used different models, so the speed comparison is product against product.
