---
title: Migrating to 1.0
description: What changes for apps, component libraries, and prompts when you move from OpenUI Lang 0.5 to 1.0.
---

Most apps upgrade without code changes. Programs that start with `root = ...`, which is what the generated prompt asks for, render as before. This page lists what does change. For the new features, see [What's New in 1.0](/docs/openui-lang/whats-new).

## Upgrade

Upgrade the OpenUI packages you use together:

- `@openuidev/lang-core`, `@openuidev/react-lang`, and the Vue, Svelte, and Angular packages are released with the same version.
- `@openuidev/react-ui` and `@openuidev/react-headless` are released with the same version.

Then regenerate any prompt or spec files you keep, for example the output of `openui generate`. The prompt text changed (see [Prompts](#prompts)).

## Breaking changes

### A program without `root` may no longer render

Before 1.0, a program with no `root` statement rendered its first component statement, or a later statement that called the root component. Now the first statement after the `$variable`, `Query`, and `Mutation` declarations is used only if it calls the library's root component. Otherwise nothing renders and the parser reports `no-root`.

```text
title = TextContent("Orders")
page = Card([title])
```

With `Card` as the root component, this rendered in 0.5 and renders nothing in 1.0. In our benchmark corpus, 151 of 24,423 programs (0.6%) stop rendering because of this.

What to do: nothing, if your prompt is generated by OpenUI. It already tells the model to write `root = ...` first. If you render stored programs from older models, watch `onError` for `no-root`. See [Entry Statement](/docs/openui-lang/entry).

### `@Card(...)` is no longer a component call

An `@` call to a name that is not a built-in, an action step, or a library function now reports `unknown-function` and evaluates to `null`. Before, `@Card(...)` acted like `Card(...)`. Components are always called without `@`.

### Data in a component-only slot is dropped

If a prop only takes components, a string, number, boolean, object, or array passed to it now reports `type-mismatch` and is left out. Before, it rendered as a blank component or stray text.

```text
root = Card(["Hello", title])
title = TextContent("Orders")
```

Here `"Hello"` is dropped from `Card`'s children. If a slot should accept text, include it in the schema, for example `z.array(z.union([TextContent.ref, z.string()]))`.

### `onError` can receive warnings

`OpenUIError` and `ValidationError` have a new optional `severity: "warning"` field. A warning means the page still rendered. If you treat every error as a failure, for example in an automatic fix loop or an alert, skip warnings:

```ts
const fixable = errors.filter((e) => e.severity !== "warning");
```

### `no-root` instead of `parse-failed`

When a response has statements but no entry renders, the React `Renderer` now reports `no-root`. It used to report `parse-failed`. `parse-failed` remains for text that yields no statements at all. Update code that checks for `parse-failed`.

### `@ToAssistant` context can be any value

`event.params.context` on a `continue_conversation` event used to be a string. It is now whatever the program passed: a string, number, object, or array. The `context` field of the `continue_conversation` action step is typed `unknown`. If your handler concatenates it into text, convert non-strings first:

```ts
const context = event.params.context;
const text = typeof context === "string" ? context : JSON.stringify(context);
```

### Built-in registry exports

These `@openuidev/lang-core` exports are removed:

| Removed                         | Use instead               |
| :------------------------------ | :------------------------ |
| `BUILTIN_NAMES`, `ACTION_NAMES` | `isBuiltin(name)`         |
| `LAZY_BUILTINS`                 | `BUILTINS[name].lazy`     |
| `BuiltinDef` type               | The entries of `BUILTINS` |

`BUILTINS` entries are now function definitions, like the ones `defineFunction` returns. They have `params` and `returns` schemas instead of a `signature` string, and their `fn` takes one object of named arguments, such as `{ numbers: [1, 2] }` for `Sum`, instead of positional arguments. Most apps do not use these exports.

## Component libraries

- Use `action()` for action props: `action: action().optional()`. The old `tagSchemaId(z.any(), "ActionExpression")` still works, but `action()` also gives the prop a `$ref` in the JSON Schema. See [Action Expressions](/docs/openui-lang/action-expressions#action-props-in-your-components).
- If you read `library.toJSONSchema()` in your own tools, action props are now `{"$ref": "#/$defs/ActionExpression"}`, and `$defs` has an `ActionExpression` entry. The schema can also have `functions` and `actions` keys.
- Every step call now evaluates to a plan, `{ steps: [...] }`, and a step that cannot run evaluates to a plan with no steps instead of `null`. If a component checks `props.action` to decide whether it has an action, check `props.action?.steps?.length` instead of `props.action != null`.
- Function and action names share one namespace with components and the built-ins. `createLibrary` throws when they collide.

## Prompts

The generated prompt changed in these ways:

- The Action section teaches one step on its own and several steps in `Action([...])`. Examples use step calls, such as `Button("View", @OpenUrl("https://example.com"))`.
- `@ToAssistant` is listed as `@ToAssistant(message: string, context?: any)`, with a note that the context can be any value.
- Built-in function lines are generated from their definitions and carry types, for example `@Count(array: any[]) → number` instead of `@Count(array) → number`. The built-in action steps are listed the same way, for example `@OpenUrl(url: string)`.
- Custom functions and custom actions are listed when the library has them.
- A prop that takes only some actions prints as `@CopyToClipboard | @OpenUrl`, with a line explaining it.

Hand-written prompts and few-shot examples that use `Action([@ToAssistant("...")])` for one step keep working. Both forms are valid.

New prompt option: `builtinFunctions: true` lists the built-in functions without turning on `toolCalls` or `bindings`.

## Stored messages

The chat in `@openuidev/react-ui` now reads and writes messages with `parseMessage` and `buildMessage`. Stored bytes are unchanged, and messages in the older `<content>`/`<context>` XML envelope still read. If you wrote your own reader for `]]>openui:` lines, you can switch to `parseMessage`. See [Storing Messages](/docs/openui-lang/messages).

The `Renderer` now accepts a stored message as `response` and strips the marker lines itself.

## Other renderers

The Vue, Svelte, and Angular renderers apply the new entry rule and report the new errors. They do not run custom functions or custom actions, and they do not render an entry that picks a component at runtime (`root = $t ? a : b`).
