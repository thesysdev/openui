Use this package to answer in a chat platform with a native, interactive card instead of markdown.
The model writes an OpenUI Lang program, and the package compiles it to the platform's own format:
Block Kit on Slack, Adaptive Cards on Teams, Rich Messages on Telegram, and interactive messages on
WhatsApp.

The package is the payload layer. It never owns webhooks, tokens, or delivery, so it works with any
transport: [Bolt](https://tools.slack.dev/bolt-js), Vercel's [Chat SDK](https://vercel.com/chat),
Bot Framework, or raw HTTP.

## Install

```bash tab="pnpm" tab-group="pkg"
pnpm add @openuidev/channels
```

```bash tab="bun" tab-group="pkg"
bun add @openuidev/channels
```

```bash tab="yarn" tab-group="pkg"
yarn add @openuidev/channels
```

```bash tab="npm" tab-group="pkg"
npm install @openuidev/channels
```

`zod` is a required peer dependency. `react`, `react-dom`, `recharts`, and `@resvg/resvg-js` are
optional peers, needed only when you [rasterize charts](#charts) with
`@openuidev/channels/ui/charts`.

The examples on this page call the model through [OpenUI Gateway](/docs/gateway) with the
[AI SDK](https://ai-sdk.dev), which adds two packages:

```bash
npm install ai @ai-sdk/openai-compatible
```

Create a Gateway key with `npx @openuidev/cli@latest generate-api-key` and keep it on the server as
`THESYS_API_KEY`.

## Entry points

| Entry point                     | Platform           | Renders to            | Notes                                                                   |
| :------------------------------ | :----------------- | :-------------------- | :---------------------------------------------------------------------- |
| `@openuidev/channels`           | Any                |                       | The engine, `MemoryStore`, and the shared types                         |
| `@openuidev/channels/slack`     | Slack              | Block Kit             | Native charts, streaming, form modals, entity selects, edit in place    |
| `@openuidev/channels/teams`     | Microsoft Teams    | Adaptive Cards 1.5    | Native tables, FactSets, and columns, inline forms, edit in place       |
| `@openuidev/channels/telegram`  | Telegram           | Bot API Rich Messages | Tables, checklists, in-card charts, inline keyboard, edit in place      |
| `@openuidev/channels/whatsapp`  | WhatsApp Cloud API | Interactive messages  | Button cards, list menus, chart images. Interactions send a new message |
| `@openuidev/channels/ui`        | Any                |                       | `ChartSpec`, `FieldSpec`, and `FormSpec` types                          |
| `@openuidev/channels/ui/charts` | Any                | PNG                   | `renderChartPng`, the chart rasterizer. Needs the optional peers        |

Slack has a high-level API, [`createSlackUI`](#createslackuioptions). The other platforms export a
channel and a prompt builder that you drive with [`createEngine`](#createenginechannel-options).

## Quickstart

A Slack bot that answers every mention with a streamed card, using Bolt in Socket Mode:

```ts
import { App } from "@slack/bolt";
import { streamText } from "ai";
import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { createSlackUI } from "@openuidev/channels/slack";

const app = new App({
  token: process.env.SLACK_BOT_TOKEN,
  appToken: process.env.SLACK_APP_TOKEN,
  socketMode: true,
});
const gateway = createOpenAICompatible({
  name: "openui",
  baseURL: "https://api.thesys.dev/v1/embed",
  apiKey: process.env.THESYS_API_KEY,
});
const ui = createSlackUI();

app.event("app_mention", async ({ event, client }) => {
  const { textStream } = streamText({
    model: gateway("openai/gpt-5.5"),
    system: ui.prompt,
    prompt: event.text,
  });
  await ui.streamCard(client, { channel: event.channel, thread_ts: event.ts }, textStream);
});

await app.start();
```

`streamCard` posts a placeholder in the thread, updates it with the partial card as the model
writes, and swaps in the finished card. The buttons on that card do nothing until you also route
interactions to [`handleAction`](#handleactionclient-payload).

## How a card works

The model replies with a program. This one uses state, actions, a query, and a mutation:

```
root = Root([header, summary, filters, newIssue])
$state = "open"
$title = ""
issues = Query("list_issues", { state: $state }, { total: 0 })
create = Mutation("create_issue", { title: $title })
header = Header("Issues")
summary = Section("You have *" + issues.total + "* " + $state + " issues")
filters = Actions([Button("Open", Action([@Set($state, "open")])), Button("Closed", Action([@Set($state, "closed")]))])
newIssue = Form("New issue", "Create", [TextInput("Title", $title)], Action([@Run(create), @Reset($title)]))
```

- **State and actions.** `$variables` are the card's state. A button carries an action: `@Set`
  writes a variable, `@Reset` restores its initial value, and `@Run` executes a mutation. Inputs
  such as selects, date pickers, and form fields are bound to variables directly.
- **Interactions do not call the model.** When a user clicks, the package runs the same program
  again against the updated state and edits the card in place. The program and its current state
  are saved per message in a [`MessageStore`](#messagestore) that you control.
- **Queries and mutations call your tools.** `Query(tool, args, defaults)` runs every time the card
  renders, on first post and after each interaction. `Mutation(tool, args)` runs only when an
  action triggers it with `@Run`, and the card renders again afterwards so queries pick up the
  change. If a query fails or no tools are configured, it evaluates to its `defaults`, so the card
  always renders.

Tools are opt-in. Without them the prompt does not mention `Query` or `Mutation`, and cards are
state and UI only. For the language itself, see [OpenUI Lang](/docs/openui-lang).

## `createSlackUI(options?)`

Creates the Slack integration. One instance owns the system prompt, the render engine, and the
per-message state store.

```ts
function createSlackUI(options?: SlackUIOptions): SlackUI;
```

```ts
type SlackUIOptions = {
  tools?: SlackTools;
  store?: MessageStore;
  interval?: number;
  rules?: string[];
  deliver?: (args: SlackDeliverArgs) => Promise<void>;
};
```

| Option     | Default             | Description                                                                                             |
| :--------- | :------------------ | :------------------------------------------------------------------------------------------------------ |
| `tools`    | none                | `{ specs, provider }`. Enables `Query()` and `Mutation()` in both the prompt and the renderer           |
| `store`    | `new MemoryStore()` | Where each card's program and state are saved                                                           |
| `interval` | `500`               | Minimum milliseconds between streamed preview updates. `chat.update` is rate limited to about 50/minute |
| `rules`    | none                | Extra lines appended to the system prompt, for house style or tool conventions                          |
| `deliver`  | `chat.update`       | Replaces how a finished card is written to its message, for example to upload charts as images          |

It returns a `SlackUI`:

```ts
type SlackUI = {
  prompt: string;
  streamCard(
    client: any,
    target: { channel: string; thread_ts?: string },
    textStream: AsyncIterable<string>,
  ): Promise<StreamedCard>;
  handleAction(client: any, payload: unknown): Promise<void>;
  handleViewSubmission(client: any, payload: unknown): Promise<void>;
};
```

`client` is any Slack `WebClient`: Bolt's `client`, the Chat SDK's `slack.client`, or
`new WebClient(token)`.

### `prompt`

The system prompt for the model. It is generated from the Slack component library, plus the tool
specs and `rules` you passed.

### `streamCard(client, target, textStream)`

Posts a placeholder message in `target.channel`, in the thread `target.thread_ts` if set, and
updates it with the partial card as `textStream` yields text. When the stream ends it renders the
finished program, writes the final card, and saves the program and state to the store.

`textStream` is any `AsyncIterable<string>` of text deltas, such as the AI SDK's `textStream`.

It resolves to a `StreamedCard`, a [`RenderResult`](#renderresult) plus:

| Field    | Description                                                                    |
| :------- | :----------------------------------------------------------------------------- |
| `ts`     | The card's message timestamp                                                   |
| `source` | The program the model wrote. Send it back as the assistant turn in the history |

While a card streams, queries show their defaults. They run once the program is complete. If the
stream throws, the placeholder is deleted and the error is thrown to the caller.

### `handleAction(client, payload)`

Handles a raw `block_actions` payload. It looks up the card by channel and message timestamp, then
either renders the card again in place or, for a form's trigger button, opens the form's modal.
Payloads for messages that are not in the store are ignored.

### `handleViewSubmission(client, payload)`

Handles a raw `view_submission` payload from a form modal. It writes the submitted field values
into the card's state, runs the form's action, and renders the card again. Form modals use the
callback id `"openui_form"`, also exported as `FORM_CALLBACK_ID`.

### Tools

`tools` has two parts, so the prompt and the renderer always describe the same tools:

```ts
type SlackTools = {
  specs: SlackToolSpec[];
  provider: ToolProvider;
};
```

- `specs` are tool descriptions: `name`, `description`, `inputSchema`, and an optional
  `outputSchema`. They are compiled into the prompt so the model can write `Query()` and
  `Mutation()`.
- `provider` has one method, `callTool(name, args)`, which runs the tool.

Any MCP server fits this shape: map its `listTools()` result to `specs` and its `callTool()` to
`provider`.

### Full example

Tools, button and input handling, form modals, and a thread that remembers earlier turns:

```ts
import { App } from "@slack/bolt";
import { streamText, type ModelMessage } from "ai";
import { createOpenAICompatible } from "@ai-sdk/openai-compatible";
import { MemoryStore } from "@openuidev/channels";
import { createSlackUI } from "@openuidev/channels/slack";

const app = new App({
  token: process.env.SLACK_BOT_TOKEN,
  appToken: process.env.SLACK_APP_TOKEN,
  socketMode: true,
});
const gateway = createOpenAICompatible({
  name: "openui",
  baseURL: "https://api.thesys.dev/v1/embed",
  apiKey: process.env.THESYS_API_KEY,
});

// 1. Tools: what Query() and Mutation() can call.
const issues = [{ title: "Fix login", state: "open" }];
const tools = {
  specs: [
    {
      name: "list_issues",
      description: "Count issues in a given state",
      inputSchema: {
        type: "object",
        properties: { state: { type: "string", enum: ["open", "closed"] } },
      },
      outputSchema: { type: "object", properties: { total: { type: "number" } } },
    },
    {
      name: "create_issue",
      description: "Create an open issue",
      inputSchema: {
        type: "object",
        properties: { title: { type: "string" } },
        required: ["title"],
      },
    },
  ],
  provider: {
    async callTool(name: string, args: any) {
      if (name === "list_issues") {
        return { total: issues.filter((i) => i.state === (args.state ?? "open")).length };
      }
      if (name === "create_issue") {
        issues.push({ title: String(args.title), state: "open" });
        return { ok: true };
      }
      throw new Error(`unknown tool: ${name}`);
    },
  },
};

// 2. One UI instance: prompt, rendering, and the per-message state store.
const ui = createSlackUI({ tools, store: new MemoryStore() });

// 3. Conversation: each thread keeps its history, and earlier cards go back to
//    the model as the programs they were generated from.
const threads = new Map<string, ModelMessage[]>();

app.event("app_mention", async ({ event, client }) => {
  const threadTs = event.thread_ts ?? event.ts;
  const history = threads.get(threadTs) ?? [];
  history.push({ role: "user", content: event.text });

  const { textStream } = streamText({
    model: gateway("openai/gpt-5.5"),
    system: ui.prompt,
    messages: history,
  });
  const card = await ui.streamCard(
    client,
    { channel: event.channel, thread_ts: threadTs },
    textStream,
  );

  history.push({ role: "assistant", content: card.source });
  threads.set(threadTs, history);
});

// 4. Interactions: clicks and input changes render the card again in place.
//    Form buttons open a modal, and submitting it runs the form's action.
app.action(/.*/, async ({ ack, body, client }) => {
  await ack();
  await ui.handleAction(client, body);
});

app.view("openui_form", async ({ ack, body, client }) => {
  await ack();
  await ui.handleViewSubmission(client, body);
});

await app.start();
```

### With Vercel's Chat SDK

The Chat SDK's Slack adapter exposes the same `WebClient`, and `event.raw` is the same Slack
payload, so only the handler wiring changes:

```ts
import { Chat } from "chat";
import { createSlackAdapter } from "@chat-adapter/slack";

const slack = createSlackAdapter({ mode: "socket" }); // reads SLACK_BOT_TOKEN / SLACK_APP_TOKEN
const chat = new Chat({ userName: "openui-agent", adapters: { slack } });

chat.onNewMention(async (thread, message) => {
  await thread.subscribe();
  const { channel, threadTs } = slack.decodeThreadId(thread.id);
  const { textStream } = streamText({
    model: gateway("openai/gpt-5.5"),
    system: ui.prompt,
    prompt: message.text,
  });
  await ui.streamCard(slack.client, { channel, thread_ts: threadTs }, textStream);
});

chat.onAction((event) => ui.handleAction(slack.client, event.raw));
chat.onModalSubmit("openui_form", (event) => ui.handleViewSubmission(slack.client, event.raw));

await chat.initialize();
```

## `MessageStore`

A card stays interactive only while its program and state can be looked up. The store is keyed by
a `MessageRef`:

```ts
interface MessageStore {
  get(ref: MessageRef): Promise<MessageState | undefined>;
  save(ref: MessageRef, state: MessageState): Promise<void>;
}

interface MessageRef {
  platform: string;
  conversationId: string;
  messageId: string;
}

type MessageState = { source: string; state: Record<string, unknown> };
```

`MemoryStore` is the default. It keeps state in a `Map`, so buttons on cards posted before a
restart stop responding. For production, implement the two methods over Redis or a database:

```ts
import type { MessageStore } from "@openuidev/channels";

const key = (ref) => `card:${ref.platform}:${ref.conversationId}:${ref.messageId}`;

const store: MessageStore = {
  async get(ref) {
    const raw = await redis.get(key(ref));
    return raw ? JSON.parse(raw) : undefined;
  },
  async save(ref, state) {
    await redis.set(key(ref), JSON.stringify(state));
  },
};
```

`createSlackUI` uses `"slack"` as the platform, the channel id as `conversationId`, and the message
timestamp as `messageId`.

## `createEngine(channel, options?)`

The engine is what `createSlackUI` is built on, and the API for Teams, Telegram, and WhatsApp. It
binds one platform's channel and returns functions over a program and its state. It stores nothing
and never talks to a transport: you send the output and save the state.

```ts
function createEngine<Out>(
  channel: ChannelLibrary<Out>,
  options?: { toolProvider?: ToolProvider | null; quiet?: boolean },
): Engine<Out>;
```

| Option         | Description                                                                                    |
| :------------- | :--------------------------------------------------------------------------------------------- |
| `toolProvider` | Runs `Query()` and `Mutation()` calls. Without it, queries evaluate to their defaults          |
| `quiet`        | Suppresses parse warnings. Use it for an engine that renders partial programs during streaming |

```ts
interface Engine<Out> {
  renderState(source: string, state?: Snapshot): Promise<RenderResult<Out>>;
  applyInteraction(
    source: string,
    state: Snapshot,
    interaction?: Interaction,
  ): Promise<RenderResult<Out>>;
  applyAction(
    source: string,
    state: Snapshot,
    actionId: string,
    value?: unknown,
  ): Promise<RenderResult<Out>>;
  submitForm(
    source: string,
    state: Snapshot,
    formId: string,
    patch: Snapshot,
  ): Promise<RenderResult<Out>>;
}
```

| Method             | Description                                                                               |
| :----------------- | :---------------------------------------------------------------------------------------- |
| `renderState`      | Renders a program. Without `state`, it starts from the program's `$variable` declarations |
| `applyInteraction` | Applies one interaction to the saved state and renders again                              |
| `applyAction`      | Shorthand for a button press or a control change                                          |
| `submitForm`       | Shorthand for a form submit: field values plus the form's action                          |

### `Interaction`

Every platform's event model reduces to one shape:

```ts
type Interaction = {
  actionId?: string;
  value?: unknown;
  patch?: Record<string, unknown>;
};
```

| Shape                 | When                                                               |
| :-------------------- | :----------------------------------------------------------------- |
| `{ actionId }`        | A button press                                                     |
| `{ actionId, value }` | A control change, such as a select or a date picker                |
| `{ actionId, patch }` | A batched submit, such as a Slack modal or a Teams `Action.Submit` |

`patch` is merged into the state first. Then `actionId` resolves to a button's action, a bound
input that is set to `value`, or a form's action looked up by form id.

### `RenderResult`

```ts
type RenderResult<Out> = {
  output: Out;
  text: string;
  actionMap: Record<string, ActionEntry>;
  charts: ChartSpec[];
  forms: Record<string, FormSpec>;
  state: Snapshot;
};
```

| Field       | Description                                                          |
| :---------- | :------------------------------------------------------------------- |
| `output`    | The platform payload. Its type depends on the channel                |
| `text`      | Plain fallback text for notifications                                |
| `actionMap` | What each interactive element does, keyed by action id               |
| `charts`    | Every chart in the card, for platforms that deliver charts as images |
| `forms`     | Form specs keyed by form id, for platforms that open a separate form |
| `state`     | The state to save for the next interaction                           |

If the model output does not parse into a root component, `output` is the channel's error message
rather than a thrown error.

## Teams, Telegram, and WhatsApp

Each platform subpath exports a channel for `createEngine`, a prompt builder, and helpers that
turn the platform's interaction payload into an `Interaction`:

| Entry point                    | Channel           | `output` type                       | Payload helpers                                    |
| :----------------------------- | :---------------- | :---------------------------------- | :------------------------------------------------- |
| `@openuidev/channels/slack`    | `slackChannel`    | `SlackBlock[]`                      | `inputValue`, `viewValues`                         |
| `@openuidev/channels/teams`    | `teamsChannel`    | `TeamsCard`, one Adaptive Card      | `decodeSubmit`                                     |
| `@openuidev/channels/telegram` | `telegramChannel` | `TgCard`, `{ blocks, keyboard }`    | `decodeCallback`, `encodeCallback`, `callbackFits` |
| `@openuidev/channels/whatsapp` | `whatsappChannel` | `WaMessage[]`, one or more messages | `decodeReplyId`, `encodeReplyId`                   |

Every subpath also exports:

```ts
function buildSystemPrompt(tools?: ToolSpec[], extraRules?: string[]): string;
```

Passing `tools` enables `Query()` and `Mutation()` in the prompt. `systemPrompt` is the same prompt
with no tools, and `library` is the platform's component library.

A Teams bot wires those pieces to its own transport and store:

```ts
import { createEngine, MemoryStore } from "@openuidev/channels";
import { buildSystemPrompt, decodeSubmit, teamsChannel } from "@openuidev/channels/teams";

const engine = createEngine(teamsChannel, { toolProvider });
const store = new MemoryStore();
const system = buildSystemPrompt(toolSpecs);

// A new message: generate a program with `system`, then render and send it.
const result = await engine.renderState(source);
const messageId = await sendAdaptiveCard(conversationId, result.output);
const ref = { platform: "teams", conversationId, messageId };
await store.save(ref, { source, state: result.state });

// An Action.Submit: restore the card, apply the interaction, and update the message.
const saved = await store.get(ref);
if (saved) {
  const next = await engine.applyInteraction(
    saved.source,
    saved.state,
    decodeSubmit(activity.value),
  );
  await updateAdaptiveCard(conversationId, messageId, next.output);
  await store.save(ref, { source: saved.source, state: next.state });
}
```

`sendAdaptiveCard` and `updateAdaptiveCard` stand for your transport. Telegram and WhatsApp follow
the same pattern with their own channel and decoder.

Platform behavior to plan for:

- **Teams.** Forms are inline. Pressing any button submits every input on the card, and
  `decodeSubmit` splits that payload into `actionId` and `patch`.
- **Telegram.** A render is one rich message with an inline keyboard, edited in place. Callback
  data is limited to 64 bytes, so option values must be short ids.
- **WhatsApp.** Messages cannot be edited, so each interaction sends the updated card as a new
  message. A card holds at most 3 buttons, and a list menu at most 10 options.

## Charts

The model writes `Chart(type, labels, values, title?, series?, xLabel?, yLabel?)`, where `type` is
`bar`, `line`, `pie`, or `area`.

On Slack, charts render natively as interactive `data_visualization` blocks. Slack allows two per
message. Further charts become placeholder blocks, which the default `deliver` drops. If a
workspace rejects native chart blocks, the default `deliver` sends the card without charts.

Teams, Telegram, and WhatsApp receive charts as images. Each chart appears in `result.charts` as a
`ChartSpec`, and in `output` as a marker your transport replaces with the uploaded image.
`renderChartPng` produces the image:

```ts
import { renderChartPng } from "@openuidev/channels/ui/charts";

for (const spec of result.charts) {
  const png: Buffer = renderChartPng(spec);
  // Upload `png`, then replace the marker for `spec.id` in `result.output`.
}
```

This entry point needs the optional peers:

```bash
npm install react react-dom recharts @resvg/resvg-js
```

| Platform | Marker in `output`                                                                          |
| :------- | :------------------------------------------------------------------------------------------ |
| Slack    | Placeholder image block, detected with `isChartPlaceholder`. Its `block_id` is the chart id |
| Teams    | `Image` element whose URL starts with `CHART_MARKER_PREFIX`, followed by the chart id       |
| Telegram | Photo block that references `attach://` followed by the chart id                            |
| WhatsApp | Message that carries a `chartId`                                                            |

To upload the third and later charts on Slack, pass a `deliver` function to `createSlackUI` that
rasterizes each placeholder and swaps in an image block before calling `chat.update`.

## Lower-level Slack exports

`createSlackUI` is built from public pieces, for when you need your own storage layout or delivery:

| Export                                                  | Description                                                                           |
| :------------------------------------------------------ | :------------------------------------------------------------------------------------ |
| `createCardPreview(client, channel, ts, render, opts?)` | Streams partial renders into a message with debounced `chat.update` calls             |
| `buildModal(spec, privateMetadata)`                     | Builds a modal view from a `FormSpec`                                                 |
| `inputValue(action)`                                    | Reads the value from one `block_actions` action                                       |
| `viewValues(view)`                                      | Reads field values from a `view_submission` view, keyed by `$variable`                |
| `chartBlock(spec)`                                      | Builds a native `data_visualization` block from a `ChartSpec`, or `null` if it cannot |
| `isChartBlock(block)`, `isChartPlaceholder(block)`      | Detect native chart blocks and chart placeholders                                     |
| `FORM_CALLBACK_ID`                                      | `"openui_form"`, the callback id of every form modal                                  |

```ts
import { createEngine } from "@openuidev/channels";
import { createCardPreview, slackChannel } from "@openuidev/channels/slack";

const engine = createEngine(slackChannel, { toolProvider });
const previewEngine = createEngine(slackChannel, { quiet: true });

const preview = createCardPreview(client, channel, ts, (s) => previewEngine.renderState(s));
for await (const delta of textStream) preview.push(delta);
await preview.dispose();
```

Give the preview its own engine with no tool provider, so partial programs use query defaults
instead of calling tools on every update.

## Custom components and platforms

To add a platform, or a component to an existing one, the root entry point exports the building
blocks the bundled libraries use:

| Export                 | Description                                                                          |
| :--------------------- | :----------------------------------------------------------------------------------- |
| `defineBlockComponent` | Defines a component from a name, Zod props, a description, and a `render` function   |
| `ChannelLibrary`       | A platform's library plus `finalize` and `errorMessage`, the input to `createEngine` |
| `walkTree`             | Walks a resolved tree and dispatches each node to its component's `render` function  |
| `RenderFn`, `WalkCtx`  | The render function signature and the context it receives                            |

See [`ARCHITECTURE.md`](https://github.com/thesysdev/openui/blob/main/packages/channels/ARCHITECTURE.md)
in the package for the rendering pipeline and the full Slack component list.
